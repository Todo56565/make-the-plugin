## PoC-1 推迟压缩一轮：**成立**

**结论**：插件在 `system-prompt/assemble` 里自己决定是否压缩，到阈值时可以不压、只记录兜底状态并给额外额度，之后在某一步再压。宿主不会抢先，因为宿主只在用量 ≥ 自己的阈值（默认 80%）时才压缩。

**证据**

| 运行 / 成员 | 进入兜底 | 兜底期间 | 换窗 |
|---|---|---|---|
| run1 alice（w2） | 5.39% 时 `deferred`，没有压缩 | 下一步写了自己的笔记 | 5.80% `fallback-note-written` → w3（用量降到 2.05%） |
| run2 erin | 5.26% `deferred`，deadline = 52569 + 16384 = 68953 | 连续 8 步 `deferred-again`（5.55%→6.64%） | 7.00% `buffer-exhausted` → w2 |
| run2 alice | 5.04% `deferred`，deadline 66779 | 多步 `deferred-again` | 7.16% `buffer-exhausted` → w2 |

**源码**

- 主路径在组装瀑布里、`next()` 之前判断（`poc/0.3.0` `src/index.ts` 的 `onAssemble`）；宿主每步先 `assemble` 再 `agent/pre-step`（`dsh-agent-loop/lib/index.js:906-911`）。
- 宿主 pressure 压缩只在超过自己阈值时动手：`dsh-compaction-basic/lib/index.js:941`、`:946` `if (measurement.totalTokens < spec.thresholdTokens) return null`。

**风险**

1. **限工具会让用量下降**：run2 alice 进兜底后工具从 38 个降到 3 个，下一步用量从 5.04% 降到 4.66%，低于 `compactAt`。兜底状态必须一直保持，不能每步按比例重新判断。
2. **模型在兜底期间结束本轮**（run2 erin、alice 都发生过，见 PoC-2）后，没有新的 token 消耗额度，也就不会走到「用完额度照样换窗」，要等下一次被唤醒。
3. 宿主阈值必须高于 `compactAt` + 兜底额度对应的比例（默认 45% + 1.6% < 80%，没有问题）；否则宿主会先压缩（仍然经过我们接管的 summarize，见 PoC-5）。

## PoC-2 兜底 restrict 与 agent-teams deny 叠加：**部分成立**

叠加语义和撤销后的状态都已实测。有三个实测问题必须在实现中处理：生效晚一步、成员换实例后我们的 restrict 丢失、tool_policy 成员会陷入死局。

### 2.1 实测可见工具列表

可见工具来自 `ctx.tools.view(agent).visible`，并用会话日志的 `request/header.header.tools`（模型实际收到的工具）交叉核对。

**普通成员（未设 tool_policy）基线，38 个**（run1、run2 的 alice、carol、dave 相同）：

```
agent_teams_claim_task, agent_teams_send_message, agent_teams_status, agent_teams_update_task,
ask_user_question, bash, context_new_window, context_remaining, create_goal, edit, exit_plan_mode,
get_goal, glob, grep, history_list_items, history_list_windows, history_read_item,
history_search_contents, interrupt_agent, job_kill, job_list, job_output, list_agents, present,
read, read_image, send_message, skill, subagent, subagent_fork, team_history, team_notes,
todo_write, update_goal, web_fetch, web_search, workflow, write
```

**队长 48 个**，比成员多出 10 个（即 agent-teams 的成员 deny 列表）：`agent_teams_add_member, agent_teams_amend_task, agent_teams_approve, agent_teams_create, agent_teams_create_task, agent_teams_delete, agent_teams_edit_plan, agent_teams_reassign_task, agent_teams_remove_member, agent_teams_resume`。成员有、队长没有的工具：无。

**叠加我们的 `agent.ctx.tools.restrict({ allow: ['team_notes', 'context_new_window'] })` 之后，3 个**（run1 alice、run2 alice）：

```
context_new_window, subagent, team_notes
```

请求头核对（run1 alice 会话）：seq 158 `request/header reason=change startsSeries=true`，工具正好是这 3 个，紧跟 seq 159 的 `tool-registry` 开发者消息（35 条 `tool-removal`）。

**撤销之后**：可见列表与基线 38 个**逐项相同**（脚本做集合比较为 True）。4 个成员协作工具 `agent_teams_claim_task / send_message / status / update_task` 恢复可见；10 个队长专用工具**仍然不可见**，说明 agent-teams 的 deny 仍然有效。请求头 seq 168 回到 38 个，seq 169 为 35 条 `tool-addition`。

### 2.2 叠加语义：交集，不是覆盖

- 源码：`dsh-tools/lib/index.js:2641` `admits()`：同一层每条限制都要放行；`:2973` `layers.every(layer => layer.admits(name))`：链上每一层都要放行。注释 `:2890` 写的是 "Restrictions intersect; scoped registrations remain visible"。
- 实测与之一致：我们的 allow 没有让任何被 deny 的工具重新出现，可见集合 = 基线 ∩ allow。
- **`subagent` 不受 restrict 影响**：它注册在成员自己的层里（`dsh-tool-subagent/lib/index.js:398` `runtimeCtx.tools.register`）；`view()` 只对继承来的工具应用限制，自己层的工具直接可见（`dsh-tools/lib/index.js:2975-2978`，注释 `:2939-2958`）。实测调用会被 agent-teams 拦下，返回 `AgentTeams member delegation limit (0) reached; report to the captain instead of spawning another agent`（`src/dsh-agent-teams/src/members.ts:1043`）。
- 被限掉的工具，模型照样调用时返回 `Error: unknown tool "read"`、`Error: unknown tool "agent_teams_send_message"` 等（run2 erin、alice），执行同样被拦。

### 2.3 restrict 会不会因为我们的名字报错

- **我们的名字不报错**：`team_notes`、`context_new_window` 由宿主层插件注册在全局层，在 `restrictableNames` 里。即使它们已经被别的层（tool_policy 的 allow）过滤掉，也不报错（run2 erin）。
- **未知名会报错**（实测）：`restrict({ allow: ['team_notes', 'no_such_tool_poc'] })` 抛出 `Error: tools.restrict() names unknown global tool "no_such_tool_poc"; known global tools: agent_teams_add_member, …`。源码 `dsh-tools/lib/index.js:2906-2908`；agent-teams 对此的说明见 `harness-compat.ts:301`。
- **推断**：设置页关掉 notes（`team_notes` 被注销）后，allow 里写死 `team_notes` 就会报错。实现时要先按 `view(agent).restrictableNames` 过滤 allow 列表。

### 2.4 实测问题一：restrict / 撤销晚一步生效

`assembly.tools` 在进入 `system-prompt/assemble` 瀑布**之前**就算好了：`dsh-system-prompt/lib/index.js:352` `tools: orderTools(collected, …)`，`:355` 才进入瀑布。所以在瀑布里施加或撤销 restrict，要到下一步才反映到请求上：

- run1 alice：施加 restrict 的那一步（step 14）请求里仍然是 38 个工具（这一步没有新的 `request/header`）。换窗后的第一步（step 15）反而只有 3 个工具，step 16 才恢复。
- **已验证的修正**：在瀑布里按当前 view 改写本步的 `assembly.tools`（PoC 选项 `syncTools`）。run2 erin 在进入兜底的同一步（step 6）请求头就变成 1 个工具（seq 61 `reason=change`）。撤销方向的同步没有得到干净的实测：run2 的两次撤销发生时，限制已经因为 2.5 的原因丢了。

### 2.5 实测问题二：成员换 Agent 实例后，我们的 restrict 丢失，agent-teams 的不丢

- run2 erin、alice：兜底状态还在时，成员一轮结束（turn/end），之后被队长重派、新一轮开始。新一轮的可见工具回到基线（erin 7 个，alice 38 个）；同时队长专用工具仍不可见，tool_policy 仍然生效。
- run3：成员一轮结束时日志出现 `agent/disposed`（bob、alice），之后同一个会话 id 再次被激活。
- 原因（源码推断，与实测一致）：agent-teams 的 deny 在每次 Agent 就绪时重新施加（`capabilities.ts:107` `onAgentReady(ctx, agent => attach(agent))` → `:93-95`）；派发时的 toolFilter 在每次创建子 Agent 时重新施加（`dsh-subagent/lib/index.js:522` `applyChildComposition` 里的 `childCtx.tools.restrict(composition.toolFilter)`，恢复时取持久化描述符 `:1931`）。我们一次性施加的 restrict 挂在旧 Agent 的 ctx 上，随旧实例一起释放。
- 实现要求：兜底状态按会话 id 保存，在每次组装（或 agent 就绪）时检查并重新施加。`42472b7` 里已加检测与重施的代码，但没有再跑一轮验证。

### 2.6 实测问题三：tool_policy 成员在兜底期间陷入死局

- erin 的 tool_policy 为 `pocread`（allow `read, grep`，在 poc profile 的 agent-teams 行声明）。基线 7 个：`agent_teams_claim_task, agent_teams_send_message, agent_teams_status, agent_teams_update_task, grep, read, subagent`。**`team_notes` 与 `context_new_window` 一开始就不可见**（tool_policy 的 allow 不含它们，`tool-policies.ts:216`）。
- 叠加我们的 allow 后**只剩 `subagent`**（交集为空，只剩自己层的工具），而且 `subagent` 会被拦。erin 尝试 `read` 和各个 `agent_teams_*` 工具都得到 unknown tool，最后结束本轮，报告「工具全部不可用」（会话 seq 73–105）。
- 所以 0.3.0 §8 的「tool_policy 不含 team_notes 时由『只拒绝一次』兜住」**不成立**：这种成员连 `context_new_window` 都看不到。可选方案：(a) 对这种成员不施加兜底 restrict，只靠提示 + 用完额度照样换窗；(b) 只在 `team_notes` 确实可见时才进兜底。

### 2.7 其他观测

- 工具集合变化会产生 `tool-removal` / `tool-addition` 开发者消息，并开启新的请求序列（`startsSeries=true`），前缀缓存失效。进出兜底各一次。
- tool_policy 交叉只测了 allow 型策略，deny 型策略没有测。

## PoC-3 无参数 `context_new_window` 触发真实换窗：**成立**

**做法**：工具只记录「本窗口请求换窗」并立即返回，下一步组装时由插件调用 `compactIfNeeded(agent, 'context-overflow')`。不在工具执行过程中压缩：那时本步的工具调用还没配对完成，`validateSurfaceRegion` 和 `selectCompactableRange` 要求边界配对平衡（`dsh-compaction-basic/lib/index.js` `toolPairingBalancedAfter`）。

**证据**

- run1 carol：第一次调用被拒（本窗口没写笔记），返回「本窗口还没写自己的笔记：先用 team_notes 记笔记再调；笔记满了就用 write 整篇精简重写。」写笔记后第二次调用被接受，下一步出现 `compaction/start→summary→end`（seq 57–60），用量 2.14% → 1.13%，进入 w2。
- run1 bob：一次（w1→w2，2.30% → 1.18%）。
- run2 carol：两次（w1→w2 seq 43–46；w2→w3 seq 126–129），两次都在同一轮里接着工作。
- 「每窗口只拒绝一次」按窗口编号记录，run1 实测拒绝一次后第二次放行。

**风险**

1. **换窗请求那一步放行的来信，下一步就被压缩掉**：run2 carol 在 step 14 收到 PING-6（seq 120），同一步调用了换窗，step 15 压缩（seq 126）。信件在信箱里已标记已读，不会再投递，只能用 team_history 找回（carol 实际就是这样找回全部 4 封的）。交接信息里的 team_history 指针是必需的。
2. **attempt_id 在换窗后丢失**：run2 carol 换窗后不知道 attempt_id，只好重新 `agent_teams_claim_task`（seq 143）来取回。交接信息里应带当前 attempt（0.3.0 §6 样例已有这一行）。
3. 模型调用工具后如果直接结束本轮，就没有「下一步组装」，要等下次被唤醒才换窗（未实测）。

## PoC-4 本窗口笔记新鲜度检测：**成立（附条件）**

**做法**：窗口编号 = 1 + 会话日志里 `compaction/summary` 的个数（与 history 模型一致）。窗口开始时间 = 最后一个 `compaction/summary` 事件的 `time`；w1 用第 0 个事件的 `time`。新鲜 = 自己的笔记文件 `mtimeMs ≥ 窗口开始时间`。

**证据**（每步都记录了 `fresh`、`noteMtime`、`windowStart`）：

- run1 carol：w1 写笔记前 `fresh=false`，写后同一窗口立即 `true`；换到 w2 后又变回 `false`，直到再次写入。
- run1 alice：w2 到 5.39% 时 `false`，于是进兜底；写入后 `true`，随即换窗。
- run2 erin：始终没能写笔记，始终 `false`，模板里写的是「上一窗口未更新」。
- 三轮共 16 次换窗，没有出现假阳性：上一窗口写的笔记在新窗口都判为未更新。

**风险**

1. 比较的是文件系统 mtime 和宿主 `Date.now()` 写的事件时间。同一台机器上一致；跨机器或网络盘时钟不同步时可能误判。
2. 子会话继承父会话前缀时，第 0 个事件是父会话的时间，窗口开始时间会偏早（未实测）。
3. 更稳的做法（推断）：同时记录 `team_notes` 对自己笔记的 write/append 成功事件（PoC 的 `onWrite` 钩子已经能拿到），两者都满足才算本窗口写过。这也和 0.3.0 §7-3「只认 team_notes」一致：用 bash 直接改文件也会更新 mtime。

## PoC-5 接管 `summarize()`，零 LLM 请求；宿主自动压缩也走它：**成立**

**做法**：经 `ctx.agentPresets.serviceFor(agent, 'compaction')` 取到引擎后，在实例上覆盖 `summarize`。团队会话返回 `{ summary: [{type:'text', text: 模板}], provider, model }`，不带 `llmStreamCall` / `rawOutput`；非团队会话调用原方法。`compactSurfaceRegion` 经 `regionDependencies()` 每次动态取 `this.summarize`（`dsh-compaction-basic/lib/index.js:1013-1016`），所以实例上的覆盖对插件主动压缩和宿主自动压缩都生效。

**零请求的证据**：插件挂了 `llm/stream` 瀑布，记录每个 LLM 请求的 `purpose`。原版摘要的 purpose 是 `"compaction"`（`dsh-compaction-basic/lib/index.js:320`）。

| 运行 | LLM 请求 purpose 统计 | summarize 调用 | 换窗次数 |
|---|---|---|---|
| run1 | 普通对话 99，session-title 1，**compaction 0** | template 4 | 4 |
| run2 | 普通对话 119，session-title 1，**compaction 0** | template 4 | 4 |
| run3 | 普通对话 54，session-title 1，**compaction 0** | template 8 | 8 |

会话日志里的 `compaction/summary` 正文就是模板（例如 run1 alice seq 98：「【交接】团队「poc030-a」…上一窗口：w1…（PoC 模板：零 LLM 调用）」），没有 `rawOutput`。

**宿主自动压缩路径**（run3，关闭插件阈值压缩，运行时把引擎 `config` 换成 `thresholdRatio 0.02, retainTokens 2000`）：8 次宿主压缩（队长 2、alice 3、bob 3）全部进入我们的 summarize。调用栈：
`compaction-basic lib/index.js:841`（自动 `agent/pre-step` 处理器）→ `:956 compactIfNeeded` → `:972 compactRegion` → `:478 compactSurfaceRegion` → `:587 summarizeCompaction` → `:1016 regionDependencies` → 插件覆盖的 summarize。

**注意与风险**

1. 先用 0.05 时，宿主只做了工具结果裁剪（`compaction/prune` 多次），用量一直没超过阈值，没有走到摘要。所以改成 0.02。宿主先裁剪、仍超阈值才摘要（`:941-946`）。
2. **宿主阈值是运行时改的**，没有用 profile：compaction-basic 的配置在 preset 声明内部，profile 里改要整份重述 preset（design §2.1）。PoC 直接替换实例的 `config`（只在 poc 分支）。
3. `serviceFor()` 每次返回**新的 cordis 代理**：用 WeakSet 判重失败，run1 每步都重新包了一层。改为在实例上打 Symbol 标记后正常（run2、run3 每个引擎只包一次）。实现时必须按这个方式判重。
4. 引擎由该 preset 的所有会话共享，所以必须保留「非团队会话走原方法」的分支。
5. 模板必须小于被替换的内容，否则抛错 `summary is not smaller than the shadowed content`（`:601`）。窗口很短时可能触发（未遇到）。
6. 宿主路径会保留一段尾部原文（`retainTokens`），插件路径用 `context-overflow` 触发，不保留尾部。两者交接后上下文形态不同。

## PoC-6 三条换窗路径下同一步到达的来信不丢：**部分成立**

**时序（源码）**：`preStep` 先认领收件箱（`dsh-agent-loop/lib/index.js:906` `inbox.claim`），再组装（`:907`，插件压缩在这里），再跑 `agent/pre-step` 瀑布（`:911`：宿主压缩在这里；agent-teams 在 `next()` 之后把放行的信标为已读，`mailbox.ts:63-64`）。认领的输入在进入本步后才追加到会话里。所以压缩那一步认领的信，一定排在压缩检查点之后。

## 汇总：对 0.3.0 实现的影响

1. 推迟压缩、兜底额度、模板摘要、换窗工具都可以照设计实现（PoC-1/3/5 成立）。
2. 兜底 restrict：
   - 叠加是交集，agent-teams 的 deny 与 tool_policy 不受影响，撤销后可见列表与基线逐项相同；
   - 必须同步改写当步的 `assembly.tools`，否则晚一步生效；
   - 必须在 Agent 重新创建后重新施加；
   - allow 列表要按 `restrictableNames` 过滤；
   - 对看不到 `team_notes` 的 tool_policy 成员，不能施加兜底 restrict；
   - `subagent` 不受 restrict 影响，但 agent-teams 会拦截。
3. 交接信息里必须有当前 attempt_id 和 team_history 指针（PoC-3、PoC-6 实测都需要）。
4. 新鲜度可以用 mtime，建议同时记录 team_notes 写入事件。
5. 换窗那一步到达的信不会丢；上一步放行的信会被压缩出上下文，只能用 team_history 找回。
