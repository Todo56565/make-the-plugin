## 一、目标形态

给 `@nanmicoder/dsh-agent-teams` 做**独立第三方补丁插件**（不修改其源码）：

- 包名形态建议：`@your/dsh-agent-teams-context`
- 通过 profile 的 `cordis.patch.yml` 按 id 追加行装载 ⇒ **装上即有、卸下即无**
- 名称 **dsh-token-budget**（2026-10-14 定名，显式隐式统一）；整体启停由 DSH 插件管理面板管理，插件内**两个开关** `notes` / `history`，默认全开；只管团队会话
- 阈值：上下文已用 **37% 提示**、**45% 强制换窗压缩**，两值可配（落点见 `plugin-design.md` §2.4）

已确认的理由：dsh-agent-teams 是第三方 npm 包，改源码会在升级时丢失且污染 `git status`；而 profile 的 patch 层天然支持按 id 插入。

**不装该补丁 = 原版社区 teams**，符合「可自己选择打开 Token Budget 还是用原版」的要求。

## 二、术语表（层级与作用域）

| 层级 | DSH 实体 | 判据（实测） | 作用域键 |
|---|---|---|---|
| **工作区** | `workspace` | 会话目录 slug，如 `--I-VMsShare--` | 路径 |
| **实例** | 一个**顶层 session** 及其全部子会话 | 侧栏一行 = 一个实例 | `sessionId` |
| **会话** | `session`（同名机制，覆盖两层） | 持久化单位 + 压缩范围单位 | `sessionId` |
| ↳ **主会话** | `session`，`delegationDepth = 0`，**无** `parentSession` 键 | `session-6680b4d6-…` | `sessionId` |
| ↳ **子会话（spawn 型）** | `session`，`delegationDepth = 1`、`origin = "subagent"`、`parentSession = "<主会话 id>"` | 本工作区 9 个中的 8 个 | `sessionId` |
| ↳ **子会话（fork 型）** | `session`，`delegationDepth = 0`、`isSeeded = true`、有 `parentSession`、**无 `origin` 键** | `55d7e1ef`（当前会话的 fork） | `sessionId` |
| **窗口** | 某**单个 session** 内的一个压缩周期 | 压缩把 surface span 换成 summary node | `sessionId` + 序号 |
| **团队** | 实例内的协作单元；一个团队 = 该实例的一个主会话 + 多个子会话 | `.agent-teams/<teamId>/` | `teamId` |

一个实例的生命周期内可能有多个团队（如先「计划团队」后「实施团队」）。

### 已确认的作用域决定

- **history 作用域不得超过当前团队**：只取当前 `team.json` + 当前团队 `inbox/*.jsonl`，不碰 `archive/`，不跨实例。
- **主会话不查看子会话预算**（用户决定：只要保证子会话静默压缩后仍能正常干活即可）。
- **笔记按工作区/团队存**（跨会话诉求）；**窗口编号按 session 存**（不跨聊天界面诉求）。两者必须是不同的键。
- **不跨聊天界面**：与「不跨归档」是同一原则的两面。

## 三、Codex 侧的做法（已取证，作设计参照）

### 3.1 头部机制

- 触发：root 会话新 turn 被接受后**异步**触发，唯一调用点 `codex-rs/app-server/src/request_processors/turn_processor.rs:704-716`（`turn_has_input && started`）。**不是压缩后、不是会话结束、不是定时器**；三条压缩路径（`compact.rs` / `compact_remote_v2.rs` / `compact_token_budget.rs`）对 `memor` 零命中 ⇒ 记忆与压缩是两条独立后台路径。
- `Feature::MemoryTool`：`codex-rs/features/src/lib.rs:1267-1272`，`key: "memories"`、`stage: Stage::Stable`、`default_enabled: false`（**有意 opt-in，非未完成**）。
- 存储：本地。路径常量 `codex-rs/protocol/src/memory_version.rs:19-20`（`"memories"` / `"memories_v2"`）；独立 SQLite 库 `memories_1.sqlite` / `memories_v2_1.sqlite`（`codex-rs/state/src/sqlite.rs:36` / `:97-112`）。
- 检索：**区分大小写的字面包含**（`codex-rs/ext/memories/src/local/search.rs:288` `.contains()`），与 history 检索同构，**均无语义/向量检索**。属有意成本选择，**不建议为 DSH 引入向量检索**。
- 注入：走 **developer 指令**通道（非工具），模型无需主动检索；4 个 memories 工具默认关闭（`codex-rs/config/src/types.rs:384` `dedicated_tools: false`）。

### 3.2 笔记粒度：Codex 是**两层**（关键参照）

**下层 = 每 thread 各写一条**：

```sql
-- codex-rs/state/memory_migrations/0001_memories.sql
CREATE TABLE stage1_outputs (
    thread_id TEXT PRIMARY KEY,   -- 主键就是 thread
    raw_memory TEXT NOT NULL,
    rollout_summary TEXT NOT NULL,
    ...)
```

**上层 = 合并成实例级共享的一份，注入给所有新会话**：

```
phase2::run → consolidation → <codex_home>/memories{,_v2}/
                                ├── memory_summary.md   ← 注入的就是它
                                ├── MEMORY.md
                                ├── raw_memories.md
                                └── rollout_summaries/
```

注入点 `codex-rs/ext/memories/src/prompts.rs:39-49`：读 `codex_home.join(version.directory_name()).join("memory_summary.md")`，截断到 **2,500 token** 后进 developer 指令。**注入不带 thread 限定**——任何新会话读到同一份。

⇒ **对 DSH 的推论**：只做「一会话一笔记」无法满足跨会话，**必须再加一层跨会话合并（consolidation）**。

### 3.3 注入与库规模解耦（最值得抄的一条）

六重收敛叠加：

- 每 thread 表内仅一行（`thread_id PK` + `ON CONFLICT DO UPDATE` + 倒流保护 `state/src/runtime/memories.rs:908,924`）
- 每次启动最多处理 2 条 rollout（`config/src/types.rs:55`）
- 30 天未使用且未入选相位 2 淘汰、批 200（`phase1.rs:97-118`）
- 相位 2 仅取 top-256（`types.rs:59,61-62`）
- `memory_summary.md` 硬校验 `< 10_000` 字节（`memories/write/src/workspace.rs:120`）
- 注入再截 **2,500 token**（`ext/memories/src/lib.rs:16`）

⇒ 记忆库可无限增长，**进入上下文的量恒定**。

### 3.4 子代理配置闸门（与「按成员预算」相关）

- `codex-rs/core/src/agent/child_config.rs:135-141` 的 `build_agent_shared_config`：当 feature `SubagentDefaultContextLimits` 启用时，显式 `config.model_context_window = None; config.model_auto_compact_token_limit = None;`（**无条件覆写**，feature 开即清空）
- `codex-rs/core/src/guardian/review.rs:151-154` 是**条件性**覆写：`if review_model.model != context.model_info.slug { … = None; }`（**仅当 review 模型与父模型不同才清空**）。与上条意图相关但触发条件不同，对比时不可等同
- 该 feature `codex-rs/features/src/lib.rs:1481-1486` 为 `Stage::UnderDevelopment` / `default_enabled: false`
- `AgentRoleOverrides`（`codex-rs/core/src/agent/role.rs:36-48`）**无任何上下文或压缩字段** ⇒ Codex 也**没有**按角色分档的压缩预算

⇒ 结论：**两边都没有按成员分档的预算**。差别是 Codex 有「可显式覆写子代理继承配额」的**闸门**（默认关闭），DSH 宿主压缩栈**连 agent 维度都不感知**。

### 3.5 交接摘要的真实细节（纠正视频报告）

- 摘要 prompt：`codex-rs/prompts/templates/compact/prompt.md`（"Create a handoff summary for another LLM…"）
- **只有前置** `SUMMARY_PREFIX`，拼在摘要**前面**（`codex-rs/core/src/compact.rs:383`）；**未找到「压缩后追加续作说明」**（UNVERIFIED）
- 保留最近用户原话：本地文本压缩路径 `COMPACT_USER_MESSAGE_MAX_TOKENS = 20_000`（`core/src/compact.rs:63`）；**remote v2 是 64_000 / 单条 agent 消息 10_000**（`compact_remote_v2.rs:78-79`）——报告未区分，引用时必须分开
- history 工具真实名是 namespaced 的 `history.list_windows` / `list_items` / `read_item` / `search_contents`（`ext/history-notes/src/tools.rs:75-88`），报告给的 flat 名全域零命中
- thread hint 上限 **4,000 字节**（`ext/history-notes/src/extension.rs:31`），超限即放弃注入；**只给指针，不含笔记正文**

## 四、DSH 侧现状（已取证）

### 4.1 插件持久化三层（「插件自有历史」的来源）

| 文件 | 写什么 | 性质 |
|---|---|---|
| `<workspace>/.agent-teams/<teamId>/team.json` | 当前团队工作状态：任务的 `subject/description/status/assignee/dependencies` + 契约（`objective/acceptance/verify/inScope/deliverables`，`src/types.ts:195-201`）+ `output`（工作者最终结果全文）+ `findings/acceptanceResults/commandsRun/changedPaths/supplementalEvidence` | **可变状态文件** |
| `<teamId>/inbox/<agentKey>.jsonl` | 每个 agent 的消息记录，一行一条；`<agentKey>` = `captain` 或成员名经 `sanitizeKey` 处理（`state.ts:436` `sanitizeKey(agentKey)`） | **行级只增不删、但文件整体原子重写**：`appendMailbox` 读旧内容后 `atomicWriteText` 整文件写回（`state.ts:430-447`）；`mutateMailbox` 会就地改写行内 `deliveredAt/readAt/deliveryClaimedAt`（`state.ts:514-542`、`acknowledgeMailbox` `:576-588` `readAt: message.readAt ?? now`） |
| `archive/<teamId>/`（归档后） | 上面整个目录搬入，供「后来的会话复盘当时怎么规划和拆依赖」 | 快照 |

**邮件箱是完整对话转录**：写入无长度限制。插件里 2000/12000 字符预算是**派发依赖产出**时的上限（`scheduler.ts:41` `DEPENDENCY_OUTPUT_MAX_CHARS = 2_000`、`:43` `DEPENDENCY_OUTPUTS_TOTAL_MAX_CHARS = 12_000`），不是邮件投递的截断。【源码 @ dsh-agent-teams 1094b84a】

**不是 append-only 的地方**：`state.ts:172-179` 的 `clearAttemptResult` 在重试时清空 `output/verdict/findings/changedPaths/acceptanceResults/commandsRun` ⇒ 重试血统不在 `team.json` 里。

**归档内容模型不可达**：`capabilities.ts:42` 的 `currentTeam` 显式 `continue` 跳过 `archive`（代码即 `entry.name === 'archive'`）。

## 五、Codex 的「换窗口」与「压缩」是两回事（重要区分）

### 5.1 Codex 打开 Token Budget 时**不做任何摘要**

`compact_token_budget.rs:16-20`（doc 原文）：

> Token-budget compaction **skips model/server summarization** and installs a **fresh context window** instead. It is still modeled as compaction so compact hooks and `ContextCompaction` turn items observe the same lifecycle as local or remote compaction.

分流点 `core/src/session/turn.rs:1461-1471`：`Feature::TokenBudget` 开启 → 直接 `run_inline_auto_compact_task(...)` 并 **return**，**完全跳过后面的 remote / local 压缩分流**。注释原文：「Compaction is the reset request, so force a new context window instead of consuming a pending `new_context` tool request.」

| 路径 | 触发 | 是否摘要 | 上下文怎么续 |
|---|---|---|---|
| **Token Budget 开启** | `Feature::TokenBudget` | **否** | 新窗口 + 重渲染 + 少量保留项 |
| 远程压缩 v2 | provider 能力 | 服务端 opaque | opaque compaction item |
| 本地文本压缩 | provider 不支持远程 | 是（20k 用户原话保留） | 摘要替换历史段 |

⇒ **「摘要」不是 Token Budget 的续接机制。**

### 5.1b 换窗是的唯一动作；压缩若发生是它的下游（已取证 `turn.rs:609-630`）

同一条代码路径上还有一个前置判定（`core/src/session/turn.rs:609-630`）：

```rust
let should_roll_over = needs_follow_up
    && (sess.take_new_context_window_request().await || token_limit_reached);
let allow_auto_compact_fallback = !should_roll_over && !token_limit_reached;
super::token_budget::maybe_record(..., allow_auto_compact_fallback).await;

if should_roll_over {
    ... run_auto_compact(..., CompactionReason::ContextLimit, CompactionPhase::MidTurn)
}
```

两条分支的语义**相反**，不能混为一谈：

| 分支 | 条件 | 动作 |
|---|---|---|
| `should_roll_over` | 有换窗请求 **或** 触到 token 上限 | `run_auto_compact(...)` → TokenBudget 短路 → **无摘要换窗** |
| `allow_auto_compact_fallback` | **既不换窗、也没触上限** 且 `base_window_tokens_remaining == 0` | 只**注入一条 developer 提示**（`token_budget.rs:201-223`），**不执行压缩** |

同一个 `maybe_record` 里还有**第三个动作**（上表未列）：当 `base_window_tokens_remaining <= reminder_threshold_tokens` 时注入一条 `TokenBudgetReminder`（role `developer`，content kind `token_budget.reminder`，文本模板替换 `{n_remaining}`；`core/src/session/token_budget.rs:178-197`、`core/src/context/token_budget_context.rs:181-200`）。它由 `claim_token_budget_reminder()` 把关，**每个窗口最多一次**：`advance()` 换窗时把 `token_budget_reminder_delivered` 复位为 `false`（`core/src/state/auto_compact_window.rs:77-89`）。⇒ Codex 的「剩余额度提示」是**每窗口一次的阈值提醒**，不是每步刷新。【源码 @ codex a07c8ebd】

⇒ **换窗是唯一动作；压缩（若发生）是它的下游。** `auto_compact_fallback_prompt`（`token_budget_context.rs:216-233`，content kind `compaction.auto_fallback_prompt`，role `developer`）只在「不允许换窗、但额度已归零」这个窄条件下注入一句提示，且该提示**不触发压缩**——它没有下游消费者，全仓 grep `AutoCompactFallbackPrompt` 仅命中定义处与 `context/mod.rs:127` 的 re-export。

`window_number` / `window_ids` 由 `start_new_context_window` 递增（`core/src/session/mod.rs:4683-4687`）。

### 5.2 `start_new_context_window()` 实际做什么

> **权威摘要（用户 2026-10-12 复制自前期取证，已逐条核对与本节一致，此后以本框为准）**
>
> `core/src/session/mod.rs:4658-4706`：
>
> 1. **过去对话整体丢弃，不做摘要**
> 2. **重渲染初始上下文**：`build_initial_context_with_world_state()` 把窗口前缀 + 普通上下文重新渲染并装进新窗口（`:4688-4690`）——**契约就是靠这个重现的，不是靠摘要**
> 3. **白名单保留项**（`RETAINED_MESSAGE_TOKEN_BUDGET = 64_000`）：
>    - `is_client_authored_developer_message`：`metadata.client_authored` 且 `role == "developer"`
>    - `is_retained_tool_output`：`metadata.client_authored` 且 `FunctionCallOutput { call_id: None, name: Some(_) }`（无匹配调用的具名输出）
> 4. **`window_number` / `window_ids` 就在这里产生**（`:4683-4687`）
>
> ⇒ 换窗时实际装入的是：**新窗口 + 重渲染的初始上下文 + 少量 client-authored 保留项**。笔记 / history 通过它们的**工具与注入通道**参与，**没有摘要**。

出处核对：本节的 Codex 侧取证原始来源是 `docs/research/context-compare/t1-codex-context-health-evidence.md` §6.1（`:450-457`）、§6.3（`:496`）、§7.3（`:596-608`），本轮据 `I:\VMsShare\_src-compare\codex` 复读确认一致。

`core/src/session/mod.rs:4658-4706` 的要点：

### 5.3 由此得到的修正设计原则

**我们注入的内容必须能「在换窗时被重渲染」，否则会丢。**

- 走 *初始上下文 / developer 指令* 路径 ⇒ 换窗时自动重现（Codex 的契约就是这样保住的）
- 走 *一次性对话消息* 路径 ⇒ 换窗时被丢弃，必须靠摘要或保留项

**精确化**：Codex 的 `<context_window>` 块（窗口 id + thread hint）与 `TokenBudgetReminder` 都**不是 system prompt**，而是 role `developer` 的**上下文消息**（`ContextualUserFragment`，`core/src/context/token_budget_context.rs:39-49`）。决定「能否跨窗口」的不是「system 还是消息」，而是「**换窗时是否被重新物化**」。DSH 有对等通道：`ctx.systemPrompt.context()` 注册的运行时上下文，以 user 角色快照进入历史，被压缩替换后**下一步自动补回**（见 §5.4 末条与 `plugin-design.md` §3）。

⇒ 笔记指针与预算提示应走**换窗/压缩后会被重新物化的通道**（DSH：`systemPrompt.section` 或 `systemPrompt.context`），而不是插件自行 append 的一次性对话消息。

## 十、方法学警告（会导致静默假阴性）

**会话日志是多帧 zstd，`node:zlib` 的 `zstdDecompressSync` 只解第一帧。**

对 5,457,836 B 的整文件调用会「成功」但只返回 189 B（首帧），从而报告「压缩事件为 0」。必须**按 magic `28 B5 2F FD` 切帧后逐帧解**。

校验数据：`94da6bb9` 解出 1696 帧 / 20,331,313 B 文本 / 3158 行 / 0 行不可解析。

**表面操作在事件顶层 `event.surfaceOp`，不在 `event.data` 里。**

查会话表面（哪个节点还在 surface 上、system head 被谁替换）时，必须读**顶层** `surfaceOp` 与 `sourceEventSeqs`。事件顶层键集合实测为：

```
["type","version","id","createdAt","cwd","isSeeded","delegationDepth","agentPreset","seq","time","data","surfaceOp","sourceEventSeqs"]
```

只查 `data.surfaceOp` 会得到「整个会话零个 surface 操作」的假阴性——而正确解析下 `session-dee7fe` 有 141 个 surface 事件（首帧即 `seq 7 system/message surfaceOp=append`）。

对应源码：`dsh-session/lib/index.js:1444-1445`（`session.append` 把 `surfaceOp` / `sourceEventSeqs` 平铺进事件对象）、`:295-307`（`surfaceOpOf` 从事件顶层读取并校验）、`:176-200`（surface 事件判定与 `append` / `replace` 两种变体）。

## 十一、Codex 的子 Agent / 多 Agent 上下文模式（已取证）

### 10.1 子 Agent 有独立窗口

- 子 Agent 是独立 Thread/Session，子配置收拢在单点 `codex-rs/core/src/agent/child_config.rs:132-165`（`build_agent_shared_config`，spawn 与 resume 共用）
- 窗口/压缩阈值由**子自己的** `ModelInfo` 解析：`core/src/session/turn_context.rs:755-758`（`model_context_window()` → 只读本 session 的 `model_info().usable_context_window()`）、`core/src/session/context_window.rs:53-95`。**父窗口不参与。**
- 用量账本显式隔离：`core/src/agent/control/spawn.rs:121-123`（`TokenUsageRecord(_) => false`，注释 "Child threads inherit model context, not the parent's cumulative usage state"）

### 10.2 初始上下文只有两种模式（关键）

- `fork_turns=none`（默认）→ 全新线程，只有工具 `message` 任务描述 + 子自己的 instructions（`core/src/agent/control/spawn.rs:799-834`）
- `fork_turns=all` → 拷贝父的**完整持久化 model context**（含父的 compaction replacement history），经白名单裁剪 `keep_forked_rollout_item`（`spawn.rs:81-125`）：丢 `Reasoning` / `FunctionCall` / `FunctionCallOutput(call_id)` / `AgentMessage` / `TokenUsageRecord`；追加边界声明 "You are now a newly spawned child agent…"（`spawn.rs:1287-1293`）；并把父的 developer 指令**逐字替换为子的**（`spawn.rs:1188-1213`）
- **`fork_turns` 只接受 `none|all`，数字也被当作 `all`**：`core/src/tools/handlers/multi_agents_v2/spawn.rs:294-303`（`"all" || parse::<NonZeroUsize>().is_ok()` → `FullHistory`；否则报错 "fork_turns must be `none` or `all`"）；`SpawnAgentForkMode` 只有 `FullHistory` 一个变体（`core/src/agent/types.rs:21-24`）。**不存在「只 fork N 轮」的部分截断**
- 端到端测试证明「父已压缩 → 子继承压缩摘要、但不继承父 developer 指令」：`app-server/tests/suite/v2/multi_agent_v2_developer_instructions.rs:447-466`

### 10.3 子压缩自己的窗口，无子 Agent 特判

压缩在 Session 层由本 session 的 turn 三点触发（pre/mid/post：`core/src/session/turn.rs:346-353, 610-628, 718-736`）。**否定证据**：对 `compact.rs` / `compact_remote_v2.rs` / `compact_token_budget.rs` 检索 `SubAgent|subagent|is_subagent|ThreadSpawn|session_source` → **0 命中**。

### 10.4 子 → 父的上下文回传：不存在

- `AgentControl` 契约全量方法（`core/src/agent/api.rs:35-165`）**无任何读子窗口/压缩状态的方法**；`list` 返回 `LiveAgent{thread_id, metadata, status}`

- **唯一的「跨 Agent 压力信号」是树级共享额度** `RolloutBudget`（`core/src/rollout_budget.rs:18-29, 47-93`）：全树共享 token 额度、每个线程各自收到剩余预算提醒——**是树级额度，不是某个子的窗口状态**
- `get_context_remaining` 读 `invocation.session` **自身**（`core/src/tools/handlers/get_context_remaining.rs:85-93`），**无法指定目标**，且受 `Feature::TokenBudget` 门控（`core/src/tools/spec_plan.rs:1401`）

- (a) 摘要型压缩把用户原话（含 spawn 任务消息）在 20k 预算内保留：`core/src/compact.rs:63` + `:574-599`（仅排除 summary 消息）
- (b) 每次换窗都重建初始上下文：`core/src/session/mod.rs:4658-4700` → `build_initial_context_with_world_state`（`:4326-4345` 重建 developer instructions）

- 注意 `new_context` 明确「不做摘要、直接开新窗口」（`core/src/tools/handlers/new_context_window.rs:13-45`），该路径下 spawn 任务消息**无专用重注路径**

### 10.6 模型层面互不可见

V2 工具面只暴露身份 + 状态。两条例外链路都不含窗口字段：(1) Guardian 读父/根的有界证据 `get_guardian_package`（`core/src/agent/api.rs:142-146`），且 fork 时会清空 `guardian_history`（`spawn.rs:1253`）；(2) 跨线程投递时抓发送者 retained_context（`core/src/agent/control/sender_context.rs`）。

### 10.7 对 DSH 设计的结论

1. **「子窗口隔离 + 无回传」是两个系统的共同语义**，不是 DSH 的缺陷 ⇒ 用户「子会话静默压缩、主会话无需知道」的选择与 Codex 一致
2. **可借鉴**：子窗口按 Agent 隔离 + token 预算按树共享的双层设计（`rollout_budget.rs` + `spawn.rs:121-123`）；以及**继承历史必须显式声明边界**（`spawn.rs:1287-1293`）
3. **前提不成立**：若 DSH 需要「父感知子的上下文压力」来做调度，**Codex 没有可抄实现**——回传通道、状态字段、工具面全都没有
4. **别抄动机**：`SubagentDefaultContextLimits` 的 why 在本检出不可证（shallow clone），只能引用其可观测语义
5. **一个 DSH 可直接改进的对照点**：Codex fork 时会 (i) 白名单裁剪父上下文、(ii) 追加边界声明、(iii) 用子的 developer 指令替换父的；而 DSH 的 `buildForkSeed` 是**逐字复制全部**（含 system 与注入的 developer 消息）。
   - **2026-10-12 复核更正**：原文接着写「因此必须按 session 重新注入，不能依赖继承」——**这个推论过头了**。子代理复核（§14.9.5）实测：CC/pi-ai 路由下 fork 子会话在自己的**第一个请求之前**就把继承来的 head 改写了（`55d7e1ef`：seed 边界 1418 → rewrite 1427 < request/header 1431）。所以「冻结副本」**模型看不到**。
   - **保留下来的问题**：父会话的动态值确实会被**逐字复制进子会话的日志**（审计污染），且**只在 in-history 路由**上才留作 node 0 被真正发送（本机未走该路由）。⇒ 结论应改为：**不依赖继承是稳妥做法，但理由不是「会被污染」，而是「继承值本就与子会话无关」**。

### 10.8 Thread hint 的真实做法（Codex 侧，2026-10-12 源码读通）

**问题**：Codex 的 thread hint 是怎么来的？是把 note 和 history 掉 API 制造成 ≤4000 字节的短索引吗？

**答案：方向对，但要改两点。** hint 由**服务端端点算好返回**，且**客户端对超限是丢弃而非截断**；上限是**告诉服务端的预算**，不是事后裁剪。

#### 10.8.1 唯一一个「生成物」端点

| 环节 | 事实 | 出处 |
|---|---|---|
| 端点 | `alpha/notes/v2/thread_hint`，POST | `ext/history-notes/src/extension.rs:125` |
| 业务参数 | **空**：`json!({})` | `:128` |
| 由客户端注入的上下文 | `{context: {session_id, current_agent_name}}` | `backend.rs:48-54` |
| 上限传递方式 | **不是截断结果，而是把上限告诉服务端**：`TruncationPolicy::Bytes(4000)` 编成 JSON 塞进请求头 `x-openai-tool-output-truncation-policy` | `:64-75`；常量 `MAX_THREAD_HINT_BYTES = 4_000`（`:31`） |
| 客户端取用 | 只取响应 `.text` 字段 | `:136` |
| 客户端二次校验 | `text.len() > 4000` ⇒ **判 Failed，整条丢弃**（不截断、不硬用） | `:140-143` |
| 空文本 | `text.is_empty()` ⇒ **不注入任何东西** | `:145-147` |
| 失败路径 | 调用失败 / 无 `text` / 超限 ⇒ **静默不注入**，仅上报 analytics `ThreadHintStatus` | `:113-144` |

⇒ **hint 正文由服务端生成，客户端看不到拼接逻辑**。我们只能看到这条契约（输入、4000 字节预算、必须回 `{text}`）。

**配置闸门**（`::46-66`）：必须有 `token_budget.use_history_notes_extension` **且** provider 是 OpenAI **且** 当前认证走 codex backend；否则 `thread_store.remove::<HistoryNotesExtensionConfig>()`，整条链路（hint + 8 个工具）都不挂。

#### 10.8.2 「推索引 / 拉内容」是两套端点，共 10 个

```
唯一生成物（服务端算好的 ≤4KB 索引，主动推）
  alpha/notes/v2/thread_hint

模型主动拉取（8 个 action，全部 POST 到后端，非本地实现）
  alpha/history/v2/list_windows / list_items / read_item / search_contents
  alpha/notes/v2/list_files_by_prefix / read_file / search_contents
                 / append_to_file / write_file
```

action → 端点映射见 `ext/history-notes/src/tools.rs:32-108`。**推的是索引，拉的是内容**——印证 §8.4「两个独立来源拼进同一 slot」。

#### 10.8.3 关键：hint 的刷新粒度是**「上下文窗口重建」**，不是每步

`contribute_thread_context` **嵌在 `build_initial_context_with_world_state` 内部**（`core/src/session/mod.rs:4374-4391`，属 `:4319` 那个函数）。该函数在生产代码里只有 **3 处**调用：

| `core/src/session/mod.rs:4689` | `start_new_context_window`（Token Budget 换窗） |
| `core/src/session/mod.rs:4753` | `record_context_updates_and_set_reference_context_item`，由 `should_inject_full_context = reference_context_item.is_none()` 把关（`:4746`）⇒ 只在初始上下文基线不存在时（首轮 / 换窗后 / 换上下文后） |

**取到之后的流向**：`context_window_hints` 收集（`:4328`/`:4384`）→ `"\n".join` → 作为**第 5 个参数 `thread_hint`** 传给 `TokenBudgetContext::new(...)`（`:4451-4463`）⇒ 落进 **`<context_window>` 消息内部**（字段定义 `context/token_budget_context.rs:15-20`）。

**顺带一个易误读点**：**MCP 的 context 贡献也 push 进同一个 `context_window_hints`**（`:4451`）。所以 `<context_window>` 块里可能同时有 notes hint 和 MCP 上下文——这也解释了 t1 §8.4 记的「两个来源拼进同一 slot」。

#### 10.8.4 对 DSH 的三条直接结论

1. **动态索引不需要实时。** Codex 的 hint 能是动态的，**恰恰因为它只在窗口重建时取一次**——它连「每步刷新」的钱都没付。它就是**窗口级**刷新，与 §14.9.4 的第二层（窗口编号）同粒度。
2. **DSH 有两个窗口级挂点**：(a) system prompt 的 variable/section——插件观察 `compaction/*` 自增，下次 `assemble()` 渲染变、`project()` 改写 head；(b) `systemPrompt.context()` 运行时上下文——内容变了就追加一条新快照，被压缩替换后自动补回。两者都**等价于** Codex 在 `start_new_context_window` 里重新取 hint。差别：(a) 每次换窗改写 surface 第 0 节点，会让 DSH 压缩本来刻意保住的 system 头前缀（`compaction-basic/src/summarizer.ts:28-31`）从第一个 token 起失配；(b) 不动 system 头。选哪个取决于 §14.9.5.4 的裁决，见 `plugin-design.md` §7。
3. **我们没有的只有那一个端点**：Codex 的索引由**服务端生成**（它掌握 notes + history 的全局视图）。DSH 没有此类服务，所以索引只能（a）由插件从 `team.json` 拼一段**稳定**文本，或（b）干脆退化成**一个稳定的文件路径指针**。**没有第三条路**——DSH 侧不存在可调用的索引生成器。

**准确的说法（撤下缓存论之后的真实约束）：**

1. **换窗作废缓存是两种机制共有的既定代价，但作废范围不同。** Codex 换窗要重付整个初始上下文；DSH 压缩**保留 system 头与工具声明**、只把 checkpoint 起的尾部重付——宿主还刻意让摘要请求复用同一前缀（`compaction-basic/src/summarizer.ts:28-31`）。⇒ 「跨窗口缓存不可依赖」对 Codex 是全量成立，对 DSH 只对 system 头之后成立；若把每窗口变化的值写进 system 头，会把 DSH 本来保住的那段前缀也作废。**是否据此选注入位置，属 §14.9.5.4 待裁决项。**
2. **但「每步改写 system 节点」仍应避免，理由换成另外两条**（与缓存无关）：
   - **每步一条 log-only 事件**：渲染文本每步都变 ⇒ `project()` 每步走 `head.text !== rendered` 分支写一条 `system/message` 事件。这是纯粹的日志膨胀与投影 churn，没有任何收益。
   - **system 头是会话的不变量，fork 会逐字复制**：`buildForkSeed`（`dsh-session/lib/index.js:924-933`）把 `system`/`developer` 消息一并复制给 fork 子会话 ⇒ 放进 system prompt 的每步动态状态，会作为**冻结快照**污染每一个 fork 后代。
3. **因此两条注入位置的判据保持不变，只是依据改了**：
   | 内容性质 | 位置 | 依据（更正后） |
   |---|---|---|
   | 稳定（契约、窗口编号） | system prompt 的 section / variable | 换窗时不丢（判据 1），且渲染不变即零事件 |
   | 每步都变（笔记、动态状态） | 对话消息 append | 避免每步一条 log 事件，且避免污染 fork 的冻结副本；代价是被压缩覆盖，需靠自身重新拉取 |

**缓存计数的事实记录**（供以后参考，不作为设计依据）：本机 `cc` 路由的事件里确实带 provider 计费口径的缓存计数 —— `session-6680b4` 的 406 条带 usage 的 assistant 消息中 402 条 `cacheReadTokens > 0`，最大单次 424,320，`cacheWriteTokens` 全为 0。来源说明见 `dsh-llm-deepseek/README.md:142`（cache 指标映射进 harness usage）与 `:180`（未变更前缀有资格复用）。**这些数字只说明「窗口内稳定前缀确实被复用」，不能用来反驳「换窗作废缓存」——两者讲的是不同层级。**

#### 14.9.5.2 我原先给的两条理由：**都被削弱或驳倒**

| 原理由 | 复核结论 |
|---|---|
| **(M-A) 每步一条 log-only 事件，纯日志膨胀** | **不能作为区分性理由**。往**对话消息**里写每步变化的内容，**同样每步写一条 `user/message` 事件**（`dsh-agent-loop/lib/index.js:1061` + `RuntimeContextProjection.project` `:334-348`）。DSH 自己就是这么干的：`dsh-time-context` 把时间作为 **user message** 经 `agent/pre-step` 注入（`dsh-time-context/lib/index.js:215-246`），默认节流 6e5 ms（`:162`），实测 408 步注入 31 次。⇒ **「避免日志膨胀」推不出「必须放到消息里」**。<br>另外术语用错了：「log-only event」在 `dsh-session` 指 `surfaceOp === undefined` 的事件（`dsh-session/lib/index.js:348-352`）；`system/message` 的 replace **是 surface 节点、模型可见、会改变请求负载**。 |
| **(M-B) fork 会拿到冻结快照 ⇒ 污染后代** | **在 cc/pi-ai 路由上被驳倒**。复制本身成立（见上表），但**本机路由下子会话在自己的第一个请求之前就把继承的 head 改写了** ⇒ 那个「冻结快照」**模型根本没看到**（`55d7e1ef`：rewrite 1427 < req 1431；子代理另举 `session-ddd5b691` seq 347 `replace@7`）。**仅在本机未走的 in-history 路由上**，继承文本才留作 node 0 并在线上作为 `system` 字段发送。⇒ 我写的「污染每一个 fork 后代」**过度断言**。 |

#### 14.9.5.3 复核后仍然成立的

1. **规范结论不变：每步都变的内容不要放进 system prompt。** 但**不能**再用「日志膨胀」或「fork 污染」当理由（后者在本机路由不成立）。
2. **仍然成立的理由只剩两条，且都比原来窄**：
   - **负载稳定性**：就地改写 head ⇒ 负载尺寸恒定；在 in-history 路由上则**每个保留版本都会被重发**（实测 63 步留 9 个 8.6–11 KB 版本，`dsh-agent-loop/README.md:160`）⇒ 那条路由上「往 system prompt 写」会**无界增长**。本机不在该路由，所以这条只是「换路由会踩」的预警。
   - **窗口内前缀复用**：`README.md:164` 明说就地改写 head「differs from its first token — in full when the node is node 0」，而 append 消息保住前缀。**这条就是被撤下的缓存论**，见 §14.9.5.4。
3. **两条注入位置判据（依据需再收窄）**：

| 内容性质 | 位置 | 目前站得住的依据 |
|---|---|---|
| 稳定（契约、窗口编号） | system prompt 的 section / variable | **换窗时不丢**（判据 1，5 次压缩零反例）；渲染不变即零事件（**但要减去合并例外**，见下） |
| 每步都变（笔记、动态状态） | 对话消息 append | 仅剩「负载不随变化累积」+「窗口内前缀复用」；**若缓存被整体排除，则此判据失去依据** |

4. **两处新的精确化（原结论的边界）**：
   - **「文本不变 ⇒ 零事件」不是绝对的**：合并（consolidation）时会先给每个保留的非空后续节点发空替换、再改写 head（`:273`/`:274`），**即使有效文本没变**。实测反例：in-history 会话 `4c3aac72` seq 127（append，len 8509）→ seq 276（`replace@7`，len 8509）——文本相同却落了事件。`dsh-agent-loop/README.md:121` 原文：「Consolidation applies even when the latest effective text is unchanged」。
   - **「每步一条」是下界**：合并时事件数 = 保留的非空后续节点数 + 1（head 改写）。

#### 14.9.5.4 悬而未决的一点：缓存论该不该整体排除

用户已明确「Token Budget 换新 context window 之后，原来的缓存本来就作废了 —— 我们本来就不用缓存」，我据此在 §14.9.4 撤下了缓存理由。但子代理复核的结论是：**区分「写 system prompt」与「写消息」的**唯一**判据恰恰是窗口内的前缀复用**，而这是**窗口内**、不是换窗时的事。

两者作用域不同、并不矛盾：

- **我在撤下时说过「两者讲的是不同层级」** —— 换窗作废缓存（跨窗口）≠ 窗口内前缀复用（窗口内）。
- 因此**准确表述应是**：缓存是**跨窗口**不可依赖（两者皆作废），但在**单个窗口内**它仍然区分两种注入位置。
- **需要用户裁决**：是把「缓存」整体排除出设计依据（那么上表第二条判据作废，只剩负载稳定性），还是只排除「跨窗口缓存」这一层（那么窗口内前缀复用仍可作为依据）。**这一点我不自行下结论。** 两个分支各自决定窗口编号 / notes hint 放 system section 还是运行时上下文，对照表见 `plugin-design.md` §7-1。
