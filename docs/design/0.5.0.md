## E4 w1 交接只发一次

**问题**：预算提醒与 w1 交接原本都是 `systemPrompt.context`。宿主把所有 context 拼成一段快照，任一项变化就整段重发（`dsh-agent-loop` `RuntimeContextProjection.project`），预算每升一档交接就跟着重发。

**做法**
- 删除 runtime context `dsh-token-budget:handoff` 及 assemble 中重算它的分支；预算提醒不变。
- 新增 `agent/pre-step` 监听：先 `next()`，reject 原样返回；窗口为 w1、日志中尚无交接、有团队身份时，在本步消息尾部追加一条 `createUserMessage`，`source = { kind: 'dsh-token-budget/handoff', form: 'instructions' }`，正文为 `initialHandoffText`，外包 `<system-reminder>`。
- “是否已发”记在窗口投影（`tokenBudgetWindow`，stateVersion 3，新字段 `handoffSent`）：随日志重放，冷启动自动恢复。投影不可用时不发。
- 压缩后不补发：任何摘要都进入 w2，由摘要位置的完整【交接】接替。

**取舍**：发出后在 w1 内切换 notes/teamHistory 开关，交接不再更新（只追加、不改写）；工具开关仍即时生效。

**测试**：`applyWindowEvent` 记录交接、`needsInitialHandoff(windowIndex, handoffSent)`。

## E1 普通子会话隐藏本插件工具

- 隐藏条件：会话是子代理（origin subagent 或 delegationDepth > 0），自己不是成员，且直接父会话不是任何活动团队的 captainSessionId。
- 不追祖先链、不处理 fork（用户 10-18：fork 相关交给另一边的快照模块，避免代码打架）。
- 时机：`agent/created`。同一会话的 Agent 会重建（成员每轮、压缩后），按会话 id 记住第一次的决定（进程内），保持前缀稳定。
- 做法：`agent.ctx.tools.restrict({ deny })`，只 deny 8 个工具中当时已注册的；随子会话销毁自动撤销。判定出错时保留工具。
- 文件 `src/team/tool-visibility.ts`；纯函数 `shouldHideTools` 测试。不加设置。
- 已知边界：创建后才打开的工具开关（如 notes）不在 deny 里，隐藏的子会话会看到新注册的工具。

### E5a 全文去重键按状态区分（10-19 已定方案 A）

**问题**：键 `<teamId>@<代>:<taskId>:<attempt>`。只回退会话与 team.json、不回退 `.context/` 的工具（单会话 rewind）会让重做的那次 attempt 整数与被丢弃的一次相同，新完成被当成「已记」：不写全文、不进待合并。

**依据**（agent-teams v0.1.25）：只有 claimed 之后才能到 completed/failed，进入 claimed 必经 `beginTaskAttempt`（attempt+1，写入新 `randomUUID()`）；终态不再转移。清空 attemptId 的只有 `cancelUnfinishedTask`（→ cancelled）与 `invalidateTaskAttempt`（→ pending）。故 completed 的 attemptId 永不清；failed 只在被打回 pending 时清，再到终态必是新 attempt 新 id；cancelled 恒为空。

**做法**
- completed / failed：`<teamId>@<代>:<taskId>:<attempt>:<attemptId 前 8 位>`；attemptId 缺失（只可能手改 team.json，空串视为缺失）退回旧键。
- cancelled：保持旧键（不进待合并，撞键只少一条取消记录）。
- 快照目录 `…/<taskId>/a<attempt>/` 改为 `a<attempt>-<id8>`（拍快照时任务处于 claimed / in_progress / completed / failed，必有 attemptId），否则重做与被丢弃那次的快照会混在同一目录。
- `ended.ts` `removeUnrecordedAttempts` 从目录名反推键：**必须同一提交**改为按新目录名反推，否则会把已记入全文的快照目录当成未到终态删掉。
- `full-cursor` 重建（`scanFullKeys` / `lastVolumeKeys`）只读标记行里的 key，不受影响；待合并短 id 由 key 哈希得到，新条目自然是新 id。
- 不写旧数据兼容（插件未发布）：旧状态根升级后现有 completed / failed 任务会以新键各重复一遍；开发机删掉 `.agent-teams/.context/` 重来（只删 cursor 不够，有分卷时会从旧键重建）。
- 改动点：`fullEntryKey`（加 attemptId）、`layout.ts` / `snapshot.ts` / `full.ts` 虚拟路径、`ended.ts` 目录解析、`pending.ts` 与 0.4.0 设计中对键的描述。
- 测试：同一 attempt 整数、不同 attemptId 都会记录；cancelled 仍用旧键；`ended.ts` 不删新目录名下已记录的快照。

### E5b 换窗状态改为写进会话日志（替代「内存状态落盘」）

**问题**：以下状态只在进程内，重启或回退后丢失，下一次请求文本与原时间线不同：兜底（进入时间、截止压力、那一轮）、本窗口已请求 / 已拒绝 `context_new_window`、最近一次写自己笔记、E1 隐藏工具的决定。

**为什么不落文件**：文件与会话日志是两份真相，任何只回退日志的工具都会让它们错位；落在日志里就随日志一起回退、一起 fork、一起被克隆。

**做法**
- DSH rc.2 有实验接口 `appendPluginRecord(session, 'plugin:…', data)`（`dsh-session` `index.ts`）：写入带 `ignorable` 的插件记录，**不进模型可见面**，resume / fork 都会带上；读不懂的读者跳过。格式迁移时「尽力保留」，丢了只等于回到全新状态。
- 本插件写 `plugin:dsh-token-budget/switch`，`data` 为 `{ kind, window, … }`：
  - `fallback`：`{ window, startedAt, deadline, turn }`，`turn` 改用日志 `turn/start` 的轮次号（替代现在的控制信号对象身份，后者重启必失效）。
  - `new-window` / `refused`：`{ window }`。
  - `note-write`：`{ window, at }`。
  - `hide-tools`：`{ hide }`，只写一次。
- 窗口投影 `tokenBudgetWindow` 折叠这些记录（stateVersion 升 4）；`SwitchStates`、`hideDecisions` 改为从投影读，内存只作缓存。
- 不需要的：压缩「已尝试」标记（丢了只多试一次）、常驻说明冻结值（只取决于角色与开关）。
- 代价：插件记录会占事件序号，e 会比现在大一点（记录本身随日志，回退后仍一致）；接口是 experimental，DSH 升级可能变，需在 E3 式的兼容检查里加一项。
- PoC 第 1 轮（10-19，DSH 0.2.1-rc.2 headless + 本地 mock 的 Anthropic Messages 服务，未调用真实模型；最小插件只写 `plugin:poc-e5b/mark` 并用投影折叠）：
  - `appendPluginRecord` 从 `@deepseek-ai/dsh-session` 正常导入（插件与宿主同一份模块）。
  - `agent/created`、`system-prompt/assemble`、`agent/pre-step`（`next()` 之后）里写：成功，各占一个 seq。
  - 写完立即 `sessionProjections.stateOf`：同步读得到新记录。
  - 在 `session/event` 监听里写：抛 `session append cannot reenter while another append is being published` ⇒ E5b 不得在 session/event 里写（现有 `session/event` 监听只读，不受影响）。
  - `--session-id` 续接（新进程）：投影从日志重放出全部旧记录，续写 seq 接着走。
  - 不进 `messages` / `system`，模型看不到。但官方 DeepSeek 客户端会在请求体的扩展字段 `dsh_session_log.events` 里带上整份会话日志，插件记录也在里面（与其他事件同等待遇，不影响提示前缀缓存）。
  - 已知副作用：一个进程卡在 D 状态时它的会话 lease 不释放，同一会话无法续接（与本接口无关，记录备查）。
  - 还没测：工具 `execute` 里写（team_notes 的 onWrite、context_new_window）；fork 后子会话是否带上记录；压缩后投影是否保留。
- PoC 第 2 轮（10-19，同一环境；mock 返回 tool_use 让模型调用插件工具，再在 assemble 里用 `compactIfNeeded(agent, 'context-overflow')` 强制压缩，前后共 5 次 headless 进程续接同一会话）：
  - 工具 `execute` 里写：成功，写完投影立即可见 ⇒ team_notes 的 onWrite、context_new_window 都可以直接写。
  - 压缩：成功生成摘要，压缩前的记录全部仍在投影里；压缩后再写、再续接，重放完整（日志只追加，压缩不删事件）。
  - 注意：headless profile 里没有 `agentPresets` 服务，插件 inject 它会一直挂起（pending）；本插件 inject 了它，所以在 headless 下不会启动（web profile 正常）。PoC 改用 `agent.ctx` 取压缩引擎。
- fork（读源码，未实测）：`buildForkSeed`（`dsh-session` `fork.ts`）把边界前的事件原样复制给子会话，插件记录也被继承。E5b 投影需与 `windowInfoFrom` 一致：**忽略 seq < inheritedEventCount 的记录**，否则子会话会继承父会话的兜底 / 换窗状态（窗口号对不上）。不做 fork 适配的约定不变，这只是让投影不出错。
- 结论：接口满足 E5b；写入点限于 agent/created、assemble、pre-step、工具 execute，不得在 session/event 里写。
- 原 PoC 待测项（已全部覆盖）：组装期间调用是否会触发「reenters another append's publication」；`stateOf` 是否在同一步内看到刚写的记录；子会话 `agent/created` 时能否写。

**测试**：投影折叠各类记录；`decide` 用轮次号判断新一轮；重放日志后状态与写入前一致。
