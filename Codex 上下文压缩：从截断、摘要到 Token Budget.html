1上下文窗口为什么会被填满00:42–03:13

上下文窗口是模型一次请求能够处理的 token 总量：发出去的内容和模型接下来要生成的内容，都要放进这个窗口里。对 Codex 这样的编程智能体来说，窗口里装的不只是当前那句话，还包括对话历史、系统指令、工具定义、读取的代码文件以及工具输出。模型接下来依据哪些信息工作，取决于窗口里还留着什么。

窗口大小同时受两种限制：输入越长，一次推理要消耗的计算、显存和时间越多；模型能否在很长内容里准确找到相关信息，又取决于它自身的长上下文能力。因此每个模型都有自己的窗口上限。以视频制作时的主流模型为例，常见 200K、400K 和 1M（100 万）token，GPT-5.6 是 1.05M，部分 Claude 与 Gemini 系列也做到 1M。

1M token 到底多大？一个非常粗略的类比是差不多一整套《三体》三部曲的文字量。不同模型的 tokenizer、代码和图片都会改变实际占用，这只用于感受数量级。

智能体消耗上下文的速度比普通聊天快得多。普通对话主要累积消息，Codex 在执行任务时还会不断搜索代码、读取文件、调用工具、运行命令，一次搜索可能返回上千行代码，一次测试可能产生几千行日志，这些工具输出同样占用窗口。任务较长时窗口仍会被填满；一旦旧历史、新消息和待生成内容相加超过上限，这次请求就无法正常处理，任务也继续不下去。

压缩的目的，就是在窗口真正装不下之前，先对已有上下文做精简和取舍，为接下来的输入与输出腾出空间。

2压缩在什么时候触发03:12–05:49

默认情况下，上下文用到模型窗口的 90%，Codex 就开始压缩。以 1M 窗口为例，默认自动压缩阈值约为 900K token，不会等到 1M 全部用完。

自动压缩阈值怎么定

源码里的 config limit 是可以额外设置的自动压缩阈值，最终 Codex 在默认的 90% 和这个配置值之间取更小的那个：阈值 = min(窗口 × 90%, model_auto_compact_token_limit)。仍以 1M 模型为例，把配置设成 200K 就会更早压缩；设成 950K 也不能突破 900K 的默认限制。

知道为什么要压缩、阈值如何确定之后，再看它在什么时候真正发生。按 Codex 当前的代码，主要有三类情况。

触发发生位置说明
用量达到自动压缩阈值新轮次开始前上一轮工具执行完、用量已达阈值，等下一条消息到来时先压缩再处理，源码里叫 pre-turn compaction
用量达到自动压缩阈值同一轮任务内部模型连续搜索、改文件、跑测试，某次工具结果返回后用量已达阈值且还要继续推理，就在下一次模型请求前先压缩，即 mid-turn compaction。所以有时没有发新消息，界面也会提示上下文已自动压缩
切换模型新模型接手前新模型窗口更小，或新旧模型使用不同的压缩格式时，先处理现有历史，再让新模型接手
手动执行 compact 命令执行时立即主动发起一次压缩

无论哪一种触发方式，都意味着 Codex 要为接下来的模型请求重新准备一份更精简的上下文。

3文本压缩：截断与交接摘要05:52–10:07

上下文精简之后，怎么保证模型还记得你的要求、知道任务做到了哪里、哪些方案试过行不通、接下来又该做什么？所以压缩的重点不只是让 token 数量降下来，还要尽量保住那些仍然会影响后续工作的关键信息。

截断长工具输出

直接舍弃最早的消息肯定不行，因为最开始往往传达项目预期和目标。换个思路，优先过滤掉重要性低的信息，一个办法是先截断过长的工具输出。Codex 把这类输出计入对话历史时会限制长度，超过限制的文本通常只保留开头和结尾，中间用省略标记代替，这样能减少日志占用的空间。

可是截断规则仍旧不会判断哪条内容更重要。如果关键信息恰好就在中间，它还是会被丢掉；而且即使每次输出都被限制了长度，任务做得久了，对话历史还是会越积越多。

交接摘要（handoff summary）

更合适的办法，也是 Codex、Claude Code 和 pi agent 广泛采用的，是让模型把继续任务所需要的信息整理成一份交接摘要。这就像员工准备交接工作：告诉下一个同事你已经做完了什么、还有什么没做、哪些方案已经试过、必须遵守哪些要求。

比如让 Codex 给一个网站项目增加登录页，要求沿用现有组件库、不能修改后端 API、还要适配手机端。经过几轮修改页面做好了，手机上的表单还有问题，这份摘要就应该交代这些要求和进度，让模型接着修表单。

  1. 分清两个角色

    运行在本机、负责读取文件、执行工具和发送请求的程序是 Codex 客户端；收到请求并实际运行模型（如 GPT-5.6）的是模型服务。生成摘要时，客户端向当前模型服务再发一次特殊请求，把现有上下文历史和"请写一份交接摘要"的要求一起交给模型。

  2. 沿用基础指令，追加 handoff prompt

    请求沿用编程助手的身份设定、工具使用方式和回答风格等基础指令，在指令和对话历史之后追加 handoff prompt。prompt 开头直接说明要为接下来继续任务的模型写一份交接摘要，随后要求交代进度和关键决策、重要约束和用户偏好、继续工作需要的数据和参考资料，最后要求简洁、结构清楚。

  3. 生成摘要后附加续作说明

    模型生成摘要后，Codex 会加上一段说明，要求后续模型根据已有进度继续干，避免重复的工作。

这里还有一个核心理念：用户原话比模型自己以前说过的话更重要。所以除摘要之外，Codex 还会额外完整保留一些最近的用户消息，最多约 2 万 token，让模型直接看到原话。沿用登录页的例子，假如摘要漏掉了"不能修改后端 API"，但这句原话被保留下来，模型仍然能看到这个要求；如果两边都没留下，后面修手机表单时就可能去改那些本来不允许改的接口。

还有一种极端情况：如果连生成摘要的请求都超过了上下文窗口限制，Codex 就不得不删去最早的一些历史消息，再请求生成摘要，这些被删掉的内容也无法被摘要覆盖。

4远程压缩与有损累积10:07–12:08

把交接内容写成一段文字是一种方案；Codex 还支持一种更进阶的压缩方案，由模型服务直接返回一份压缩后的数据供后续请求使用。这个叫远程压缩，也是连接 OpenAI 服务时 Codex 目前默认使用的方式。

远程压缩与文本摘要解决的是同一个问题，关键区别在于返回形式。文本摘要明确要求模型写一段人也能读懂的交接文字，而远程压缩返回的不再是可读的文字。OpenAI 官方把这个返回信息描述为 opaque encrypted content，用来保存模型对之前对话的 latent understanding。可以把它理解成一种给模型读取的压缩状态，是模型和模型之间的语言；至于它到底长什么样，OpenAI 并没有公开。

关于返回形式

它大概率不是 KV cache 或者 hidden state 之类的形式，更接近一种内部加密后的 token。这属于推测，来源并未确认。

loss-aware 与多次压缩

远程压缩的特点在于模型专门训练过。OpenAI 称之为 loss-aware compression：它让模型自己学会优先减少对未来行为无影响的信息，并不以压得最短为目标，所以效果会比普通的一段 summary prompt 要好。当然，这种方式依旧是有损的，压缩模型依旧会失忆。

文本摘要和远程压缩还有一个更致命的问题：长任务可能要总结很多次，很容易最后变成"摘要的摘要的摘要"。第一次压缩时"不能修改后端 API"被漏掉了，第二次模型读的是已经漏掉要求的摘要，再怎么总结也不能凭空把这个要求补回来。一轮又一轮的压缩，很可能就像综艺节目里的传话游戏，越传越偏。

三种方式对照

方式压缩或交接形式适用位置主要局限
工具输出截断只保留长输出的开头和结尾，中间以省略标记代替单条工具输出过长时不判断内容重要性，关键信息在中间仍会丢；历史总量仍会累积
文本交接摘要模型生成可读的交接文字，另保留最近约 2 万 token 用户原话需要跨轮交接任务状态时有损；多次总结会累积丢失
远程压缩模型服务返回不可读的 opaque encrypted content（latent understanding）连接 OpenAI 服务时的默认方式有损；内部形态未公开；多次压缩同样可能累积丢失

5Token Budget：主动规划与多窗口12:40–14:54

前面几种方式有两个共同特点：它们基本上都是发现上下文快满了才临时要求模型总结，很被动；而且本质上都是在做压缩，只要是压缩就无法避免传话游戏的问题。能不能主动一些，让正在做任务的智能体提前就准备好交接的内容，有没有可能不做压缩？Codex 的 token budget 尝试的就是这种思路。

目前在 Codex 里它还是默认关闭的，最近几天也有不少人提醒打开这个功能。该机制早在今年 6 月就有了，不过 8 月底最关键的 history 和 notes 机制才加入进来，这期间 Codex 也在持续迭代。

让模型知道自己还剩多少

token budget 给模型一个 get context remaining 的能力，模型可以主动查询自己还剩多少 context 能用，比如客户端回答"这个 context window 还有 40k token"。有了这个信息，模型就能主动做一些 context 的生命周期规划。

  • 还剩 40K — 可以继续深入构建项目。
  • 还剩 12K — 不应该再展开一个大型开发任务。
  • 还剩 6K — 开始做收尾工作，保存好状态。
  • 接近 0 — 不再继续任务，转而开启一个新的 context window。

这里还有一个关键点：原来是同一个 context window 不断压缩，现在是窗口 1 满了就新开窗口 2，窗口 2 满了再开窗口 3。token budget 的核心设计，是把"一直压缩一个 context window"变成"管理多个 context window"。

Codex 也并不是完全依赖模型主动查还剩多少窗口。系统还配置了 reminder threshold tokens，当剩余 token 下降到某个可配置的阈值时，会主动往上下文里插入 developer reminder，默认提醒模板告诉模型当前上下文只剩 N 个 token、很快会被重置，重置以后当前窗口里的消息不会继续带进新窗口，但笔记和历史记录可以保留。

6持久笔记与 History 检索15:02–19:43

持久笔记

换了窗口确实不是压缩，但上个窗口里的信息怎么交接过来？作者自己很长一段时间应对窗口限制的方法就是让模型记笔记：干了什么、总结了什么经验或教训都记下来，并在项目的 AGENTS.md 里要求模型持续记笔记、开始工作前先读笔记。对跨会话的任务这个方式非常有效，因为笔记就在那儿，是一个固定的 Markdown 文件，模型随时可以去查看，而不是跟着上个会话石沉大海。Codex 的 token budget 机制里也设计了一个持久化笔记的能力。

笔记由 agent 边做边记并清理过时内容。沿用网站的例子，agent 可以调用写文件工具创建一份登录页进度笔记，覆盖目标、关键约束和决策、进展问题和下一步，还要保留一些重要信息对应的 window ID 和 item ID，这个 ID 索引很重要。

切换到新窗口后，Codex 的 history notes extension 会请求一个 thread hint，最多只有 4000 字节，作为一个小提示注入到新的 context 中。它不会包括笔记里的具体内容，只是类似说"之前有一份笔记，应该先去读一下"。

History 查询接口

笔记不能保证模型真的把重要信息都记下来了，所以除了笔记，token budget 还有一个关键机制 history，也就是历史记录的查询接口。

接口作用输入 / 筛选
history_list_windows列出 window ID 和 item 数量无；每个 context window 都有一个 ID
history_list_items返回具体的会话消息内容按 window、角色（user / assistant / tool / system）以及更具体的工具名筛选
history_search_contents用关键词定位信息所在的窗口与消息关键词；window ID 可选，没有索引也能搜
history_read_item读取指定的一部分会话内容window ID + item ID

笔记当然不能保证记下所有的信息，不过它可以承担一个 working memory 和索引的作用：告诉 agent 任务现在是什么状态，以及过去哪些东西值得再深入 history 里看。

一次实际检索

  1. agent 切换到新的上下文窗口后，先收到一个很小的 thread hint，于是知道这个任务不是刚开始的、自己留过笔记，然后调用读文件工具查看 notes。
  2. 看完之后，它了解了当前的状态与约束。note 里说"不能修改后端 API"，但这是个结论，agent 想看看原文来判断这到底是上一轮模型自己的判断，还是用户明确要求的。note 留了具体索引，它就可以调用 read item 工具获取 history 里具体的原始消息。
  3. history 的 window ID 在 search contents 里是可选的。即便没有索引、不知道信息来源于哪个 window 和 item，也可以用关键词搜索，比如搜"后端 api"得到匹配 item，再去 read item。

这个机制整体看起来确实很巧妙，但对 agent 的要求也不低：要意识到某个信息很重要并写进 notes，后来需要详细信息时还要想到去 history 里找、并且搜对。而且现在的搜索机制是包含关系的查询，不是语义检索，所以 token budget 也仍然有不少优化空间。

但能看到的是，上下文窗口的处理已经从压缩问题变成了 memory 的管理和检索问题。

7长任务的实际做法：把关键信息放到文件与 Git19:47–21:39

既然压缩和 token budget 都还是会出现错误，实际做项目时还能做些什么？一个核心原则是对话不应该成为 source of truth，要把关键信息写成持久的文件。token budget 相当于系统已经帮我们做了一些事情，但我们自己也可以更主动地去控制。

OpenAI 自己在使用 Codex 进行 agent-first 工程实践时，就采用了类似思路：把代码仓库作为 system of record，把 AGENTS.md 作为 table of contents，告诉 agent 去哪里寻找需要的知识。

  • 复杂任务的状态文件 — 可以构建 execution plan、progress.md、handoff.md、decision log 等任务状态文件，然后把这些文件版本化放进仓库里。
  • git 作为 agent memory — Anthropic 的长程 agent 任务指南里也提到，git 本身就是非常强的 agent memory：让 agent 在每轮任务结束前更新 progress file 并提交 git，新的 agent 开始工作时先读取 progress file 和 git log，理解上一轮完成了什么、当前代码处于什么状态，再继续下一步。
  • 保存演进轨迹 — git 不仅保存代码，也保存了项目演进的轨迹，让 agent 可以通过 git log、git status、git diff 重新建立对过去工作的认识。

这些文件的具体要求、格式都可以按照你的需求去定制。关键在于要建立一套稳定的习惯：每完成一个可验证的阶段，或方案发生重要变化时，就更新这些文件，并且在压缩发生后或开启新会话时先重新读取。
